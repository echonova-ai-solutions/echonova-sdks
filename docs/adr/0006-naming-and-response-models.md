# 6. Naming across languages, faithful responses and lenient parsing

Date: 2026-11-09

## Status

Accepted

## Context

The API's own naming is not uniform:

- Request JSON and responses use camelCase (`voiceId`, `numSteps`). Speech to Text form fields use snake_case (`identify_speakers`). Sound Cleaning form fields use camelCase (`cutoffFreq`).
- Creating a job returns `jobId`, while job objects use `id`. Text to Speech returns `audioUrl`, while Sound Cleaning returns `outputUrl`.
- An optional field with no value may arrive as `null` or be absent. Clients must treat the two the same.
- The API changes additively: new fields, new enum values, new event types.

Each language also has its own conventions, and users expect them.

## Decision

### One naming convention per language for parameters

| Concept | Python | TypeScript | Dart |
| --- | --- | --- | --- |
| Clients | `EchoNova`, `AsyncEchoNova` | `EchoNova` | `EchoNova` |
| Services | `text_to_speech`, `speech_to_text`, `sound_cleaning` | `textToSpeech`, `speechToText`, `soundCleaning` | as TypeScript |
| Methods | `generate`, `transcribe`, `clean`, `voices.list`, `jobs.create`, `get`, `list`, `delete`, `wait`, `export`, `download`, `find_candidates` | camelCase of the same | as TypeScript |
| Streams | `connect()`, then `synthesize`, `enqueue`, `speak_stream`, `cancel`, `interrupt`; `send_audio`, `end_segment`, `set_terminology`, `stop`, `feed_from` | camelCase of the same | as TypeScript |
| Parameters | snake_case (`voice_id`, `num_steps`, `cutoff_freq`) | camelCase, matching the API JSON (`voiceId`, `identifySpeakers`) | as TypeScript |
| Errors | ADR 0005 | ADR 0005 | ADR 0005, with an `Exception` suffix |

- The SDK maps each parameter to the API's spelling internally. Callers never need to know which endpoint uses which case.
- `terminology` is a JSON string inside multipart requests and an object on the stream. Callers always pass a structured value, and the SDK serializes it.
- `spec/mapping.json`, generated by `tools/build_mapping.py`, records every operation, parameter and stream message with its name in each SDK. The SDKs' tests check their names against it.

### Responses are faithful to the API

- Response models keep the API's field names, converted only to the language's case. `jobId` stays distinct from `id`, and `audio_url` from `output_url`. The SDK doesn't rename fields to make them look consistent, so the API reference stays accurate for SDK users.
- Methods that take a job, such as `get()` and `wait()`, accept either an ID or any job object, which removes the `jobId` and `id` friction where it matters.
- The SDK sends only the parameters the caller set. It doesn't fill in defaults, so the server's defaults apply.
- The SDK doesn't copy the server's validation, such as text length or value ranges. Limits change, and a client-side copy would reject valid requests. The exception is protocol framing the SDK must respect to work at all, such as the 64 KiB WebSocket frame limit.
- The SDK exposes only what the API offers. It doesn't invent capabilities, such as a multi-item batch endpoint.

### Models are lenient

- Unknown fields are kept. Every model keeps the original payload in `raw`.
- Missing fields read as `None`, `undefined` or `null`. A field is required only if it is guaranteed in every state.
- Numbers parse from integers, floats or numeric strings. Timestamps parse to the language's date type, and the raw value stays in `raw`.
- Enums are open: an unknown status or event type parses instead of raising. Unknown stream events become `UnknownEvent`.
- Only fields the SDK's own logic depends on, such as a job's ID and status, raise `ProtocolError` when missing.
- Results that may grow come back as wrapper types (`Page`, `VoiceList`), so the API can add fields like totals without breaking callers.

Per language:

- **Python:** responses are frozen, slotted dataclasses built by a tolerant parser, with `.raw`, `.request_id` and `to_dict()`. Request parameters are `TypedDict`s, so callers can pass plain dicts and still get type checking. There is no pydantic dependency.
- **TypeScript:** interfaces mirror the API JSON in camelCase, matching the API docs one to one. Enums are open unions (`'completed' | 'failed' | (string & {})`). There is no runtime validator.
- **Dart:** immutable classes with a tolerant `fromJson` and `raw`. Enums carry an `unknown(rawValue)` case. Events and exceptions are `sealed`.

## Consequences

- Additive API changes don't break any SDK.
- Code samples in the API reference translate directly to the SDKs.
- Some inconsistency from the API stays visible (`jobId` and `id`), on purpose.
- The SDK doesn't catch invalid input before sending it. The server's `InvalidRequestError` carries its exact message instead.
- Final method names are reviewed before the first beta. After 1.0, renaming any of them is a breaking change.
